	<h3>Executive Summary</h3>
	<div><p>
&nbsp This database contains certain ways in which a library keeps track of the on goings in its facility. 
The database will be used to generate several reports. Using queries, we will be able to answer 
questions that arise. We will do this by running the queries against the database which will in turn
give us visual representations of the query. The implementation of the database contains 7 tables. 
These tables provide information about our books, libraries, and customers. The database tables 
include the following: Library, Collections, Books for sale, Books Checked out, Penalty, and Members.
These tables represent the main entities of the application and contain links that define the 
relationships between each entity. The information in the table Library includes the library ID, 
the name of the library, the city, street, state and zip code the library resides in, the email 
and phone number to contact the library and hours-of-operation. The purpose of library table is to 
hold and describe our in-house libraries. Attributes defining collection are as follows: ID, title, 
author, genre, page number, year published, publisher, and sale. The purpose of collection is to 
describe the genre of books. Attributes defining books-for-sale are as follows: BFS-ID and price. 
The purpose of this table is to describe books for sale. Attributes defining Books-Checked-out are: 
BCD-ID, date-checked-out, date-to-be-returned and date-returned. The purpose of the table books 
checked out is to keep track of the books checked out. Attributes defining Penalty are as follows: 
penalty ID, and fee. This table is a product of books not returned on the proposed date when checked
out. Lastly, we have the Members table. Attributes defining members table are as follows member ID, 
first and last name, street, city, state, zip code, email, and phone. The purpose of this table is 
to describe and keep track of the customers associated with this library.
</p></div>

<div>
	<h1>Detailed Description on relationships, cardinalities and identifiers for both database 
    design and database model</h1>
    <h3>Library and Collections</h3>
    <ul>
    	<li><b>Relationship:</b> the relationship between library and collections is one to many. 
        This because collection can belong to only one library, while a library can have many 
        collections. This is also an Identifying relationship because collection can’t exist 
        without a library.</li>
		<li><b>Cardinalities</b><br>
		Library == The minimum cardinality here is one while the maximum is Many. <br>
		Collections == The minimum cardinality here is one while the maximum is one.</li>
		<li><b>Identifiers</b><br>
		Library == Library-ID<br>
		Collection == ID, Library-library-id</li>

    </ul>
    <h3>Collections and Books for Sale</h3>
    <ul>
    	<li><b>Relationship:</b> the relationship between collections and books-for-sale is many 
        to many. This is because many books can be sold from many and a collection can have many 
        books sold which belong to many collections. It is a non-Identifying relationship. This is 
        because they are both strong entities meaning they can exist without the other. It also has 
        an intersecting table collection-has-books-for-sale with its identifiers.</li>
		<li><b>Cardinalities</b><br>
		Collections: Minimum cardinality is one while maximum cardinality is one<br>
		Collections-has-books-for-sale: Minimum cardinality is one while maximum cardinality is 
        many<br>
		Books-for-sale: Minimum cardinality is one and maximum cardinality is one.<br>
		Collections-has-books-for-sale: Minimum cardinality is one while maximum cardinality is 
        many</li>
		<li><b>Identifiers</b><br>
		Collections: ID, Library-library-id<br>
		Books-for-sale: BFS-ID, Member-member-id<br>
		Collections-has-books-for-sale: collection-id, collection-library-library-id, 
        books-for-sale-BFS-id</li>

    </ul>
    
    <h3>Collections and Books Checked out</h3>
    <ul>
    	<li><b>Relationship:</b> The relationship between collections and books-checked-out is 
        many to many. This is because books can be checked out from many collections while many 
        books checked out can belong to many collections. It is a non-identifying relationship 
        because they are both strong entities meaning they can exist without the other.</li>
		<li><b>Cardinalities</b><br>
		Collection: Minimum cardinality is one while maximum cardinality is one<br>
		Collections-has-books-check-out: Minimum cardinality is one while maximum cardinality is 
        many<br>
		Books-check-out: Minimum cardinality is one and maximum cardinality is one.<br>
		Collections-has-books-check-out: Minimum cardinality is one while maximum cardinality is 
        many<br>
		<li><b>Identifiers</b><br>
		Collections: ID, Library-library-id<br>
		Books-check-out: BCO-ID, Members-member-id.<br>
		Collections-has-books-check-out: collection-id, collection-library-library-id, 
        books-check-BCO-id.</li>

    </ul>
    
    <h3>Books Checked out and Penalty</h3>
    <ul>
    	<li><b>Relationship</b>
		The relationship here is one to one. This is because a book returned on a wrong date will 
        warrant a specific penalty, and panalties can only belong to a certain book checked out. 
        This is an identifying relationship because penalty is a weak entity that depends on 
        books-check-out.</li>
		<li><b>Cardinalities</b><br>
		Books-check-out: minimum cardinality one maximum many<br>
		Penalty: minimum cardinality one maximum one.
		<li><b>Identifiers</b><br>
		Books-check-out: BCO-ID, Members-member-id<br>
		Penalty: Penalty- id<br></li>
    </ul>
    
    <h3>Books for Sale and Members</h3>
    <ul>
    	<li><b>Relationship:</b> the relationship between books for sale and member is one to many.
        This is because one specific copy of a book can only be sold to one member, while a member 
        can buy man books. It’s a non-identifying relationship this is because they are both strong 
        entities meaning they can exist without the other.</li>
		<li><b>Cardinalities</b><br>
		Books-for-sale: minimum is one maximum one<br>
		Members: minimum is one maximum many</li>
		<li><b>Identifiers</b><br>
		Books-for-sale: BFS-ID, Member-member-id<br>
		Members: member-ID</li>
    </ul>
    
    <h3>Books Checked out and Members</h3>
    <ul>
    	<li><b>Relationship:</b> the relationship between books checked out and members is one to 
        many. This is because a book can only be checked out by one member while one member can 
        check out many books. It’s a non-identifying relationship this is because they are both 
        strong entities meaning they can exist without the other.</li>
		<li><b>Cardinalities</b><br>
		Books-check-out: minimum cardinality one maximum one<br>
		Member: minimum cardinality one maximum many</li>
		<li><b>Identifiers</b><br>
		Books-check-out: BCO-ID, Members-member-id<br>
		Members: member-ID</li>
    </ul>
